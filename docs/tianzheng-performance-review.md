# 天正 T30 性能评审与首轮优化

本文先记录只读评审和基线，末尾记录获准后的首轮实施。基线为 `fe1b119` 的阶段性适配；
65/500 表示有限配方已有实机证据，不表示所有模式已支持。

## 评审关卡

1. **固定范围**：一个可复现的用户操作、输入、对象类型/数量、图层/表格规模、
   CAD/MCP版本与进程代际；区分冷启动、热请求、客户端等待和服务端执行。
2. **独立评审**：COM/快照、协议/守卫/调度、历史证据/验收设计三个视角。
   子智能体只读源码或离线运行，不连接CAD、不部署、不改业务代码、不创建子任务。
3. **证据分级**：A=当前实机计时；B=已有实机记录；C=离线计数/测试；
   D=静态推断。没有耗时字段的JSON和文件mtime不能作为命令耗时。
   离线调用数、注入延迟及理论复杂度不得冒充真实加速。
4. **交叉质疑**：每项候选列出反例、可能更慢的输入、尚缺的测量；
   主线程核对路径和数字，区分已证实瓶颈与待验证假设，再作优先级决定。
5. **后续实施准入**：先补分段计时，再用相同夹具做交错的旧/新版本比较；
   结果等价和安全不变量先通过，速度提升才有效。不在本轮擅自发布、部署或push。

## 必须保留的不变量

- 全部图纸身份、revision、worker_generation、lease、幂等与PID绑定检查；
  新鲜context不能跨写操作复用，跨请求缓存必须明确失效机制。
- 选中对象的语义/几何后置条件，以及未选对象、对象数量、图层环境的对应检查。
  TSpArea曾修改无关墙/门，不能靠只检查目标对象缩短全图检查。
- STA串行与不确定写入不重试。不得并发执行CAD命令，也不得并行访问同一COM对象。
- 空自定义对象危险属性保护、禁用AddCustomObject/ObjectDBX路线。
- 未实测的模式不升级通过；超时阈值变大或异常被忽略都不是性能优化。
- 原项目禁止测试写入；本轮只有主线程可对已确认独立测试图作只读测量。
  首次system.ensure_ready且dispatcher.loaded=true；崩溃/多实例歧义立即停止；
  超时先检查真实界面，不自动ESC、重发、重启或关闭CAD。

## 基线与后续验收矩阵

| 维度 | 场景 | 必须记录 |
|---|---|---|
| 无CAD对照 | catalogue/describe | 墙钟、响应字节、会话冷/热状态 |
| 身份成本 | transaction.context | 单请求墙钟、doc/revision/generation |
| 全图读取 | inspect：墙/柱/门窗/文字/房间/表格混合图 | 对象类型分布、格数、响应字节、失败/重试 |
| 少量目标 | 一个墙的TGetExtend只读测量 | 目标数/总对象数、是否重复全图扫描 |
| 后续写基线 | 属性修改、原生命令、模板复制 | guard/排队/前快照/命令/后快照/验证/序列化分段 |
| 规模与边界 | 小图、当前混合图、较大图、较多表格 | 核实安全的独立夹具，不能向原项目加测试对象 |
| 非成功路径 | COM拒绝、超时、错图/错revision、幂等重放 | 返回状态/不确定状态与副作用必须等价 |

本轮热请求每场景至少5个样本，报告全部样本、median/min/max；样本少不报告p95。
正式优化验收建议每场景至少30个配对样本，采用ABBA交错顺序，报告median/p95与
失败率、重试次数、对象/图层差异。显著耗时原因未分离时不承诺加速百分比。

## 子智能体统一输出

每条发现必须包含：操作及路径/行号、证据级别、可复现数字或调用次数、成本来源、
建议改动边界、预期收益（无法定量则明确未知）、风险/反例、验证方式、优先级。
优先级不做无依据的加权分数：P0=测量/正确性前提；P1=证据充分、低风险的重复工作；
P2=需额外验证的字段/批量访问；P3=跨请求缓存、增量变更集等高风险架构改动。

### 已证实的工作量，不冒充实机耗时归因

1. **全图读取随规模增长。** 离线直接调用现有快照：单线/墙/柱/12格表的
   Python代理访问数38/38/42/67（含固定开销），缺失属性20/10/21/25。
   这些缺失率由假对象字段配置决定，不代表实际T30能力，也不是COM RPC计数。
   可选属性的AttributeError本来就不重试，不能把“删四次重试”当这部分的优化。
2. **前后扫描不是任意重复。** 单目标放在86面合成墙中仍作两次全图快照，
   共6204次代理访问；第二次快照前修改未选墙高度，现有检查正确拒绝。
   真实TSpArea面积正确但无关墙标高/门窗台高被改，同样证明局部目标验证不足。
3. **当前热路径没有反复启动CAD。** inspect/measure均2次native context RPC、
   1个Python STA工作项，快照分别1/2次；热路径ready/ping次数为0。
   它们不走file IPC的100ms轮询，不能把该轮询或20ms空闲message-pump周期算进每次请求。
4. **历史计时不能充当新旧基线。** 77份结果中只有9份含36个真实计时值，
   部分包含建夹具、额外inspect、限流或写盘；1523份原始响应没有独立命令耗时。
   zoom后的4秒客户端等待、原生配方的300ms等待属于不同阶段，且后者不在本轮读路径。

### 最终优化顺序

| 顺序 | 决定及代码边界 | 为什么这样排 / 准入条件 |
|---|---|---|
| P0 | 先补阶段计时和计数：`server`、`transport_guard`、`com_sta`、T30快照/环境/验证 | 区分HTTP、队列、mutex、前后快照、属性缺失/拒绝、命令、验证、JSON；内存累计，结束一次输出，不能每个getter同步写日志。先量化观测自身开销 |
| P1 | 第一项小型优化实验：`_t30_environment`请求内复用Layers集合引用 | 85层时取Layers 86次；保留85层的所有字段检查，局部引用不跨写、不跨请求。预测少85次Python查找，不承诺省85次COM RPC或固定秒数 |
| P2（主线） | 按已验证类/接口制定字段读取计划，再验证原生端串行批量读取 | 减少无意义字段探测及边界往返，保留全图既有字段覆盖与前后比较。先原生常见类，T30/未知版本严格回退；表格0/1基、行列边界、缺失与瞬态错误均需等价测试 |
| P2（单独候选） | TModElev同阶段后快照复用 | 当前成功路径3次快照有机会省1次，但把投影验证移进回调会改变失败回滚语义，主线程不把它当作无条件低风险P1。先锁定原错误/副作用/回滚契约，不与其他改动捆绑 |
| P1（响应性支线） | catalogue/describe的有界离线排队与CAD执行队列分离 | 离线探针证实零CAD目录也会排在长CAD请求后。仅利于并发响应，不提升本轮串行读速度；保留预算/大小限制，CAD仍最多一个执行项 |
| P2/P3（后置） | 经可靠就绪条件验证后研究固定等待；跨请求快照缓存/增量变更集暂缓 | 不直接删300ms/4秒等待；不缓存过期context或依赖未证明完整的revision事件。小图、外部编辑、Undo/Redo、切图/重启、同句柄重建都可能破坏收益或正确性 |

不优先做context消重：当前9.57ms对照秒级读取没有显示它是主成本；前后身份时点不同。
不采用减少未选对象/表格字段校验、并发COM、加大超时或吞异常的“提速”。
评审结束时仅确定实施顺序，当时没有候选版本或实测加速百分比。

### 单独的安全准入发现：named-pipe写后读失败重发

`native_pipe.py:313–341`的OSError重试覆盖open/write/read整个区段。离线故障注入：
连接前失败为opens=2/writes=1；首次写成功后read抛OSError为opens=2/writes=2。
主线程复跑一致。此处说的是两次发送，**不是证明CAD重复提交**：
`native/AutoCADMcp.Plugin/CadDispatcher.cs:44–53,104–109`有成功结果的幂等重放。

在修改传输重试/并发/超时时，应先单独审查这一边界：区分发送前失败与发送后不确定，
覆盖部分写、读失败、EOF、超时及延迟完成，核实journal/服务端幂等和收敛状态。
它不是当前只读秒级延迟的已证实原因，本轮不顺带改动，也不把它描述成已修复。

## 首轮实施与实测（2026-10-15）

用户随后授权实施、提交和push。本轮只落实请求内图层集合复用与两段读回计时，
不等于全部性能候选、完整P0计时矩阵或500名称适配已完成。

### 改动边界

- `_t30_environment`只在当前调用内保留`document.Layers`引用；85层时该属性查找
  从86次降为1次。每层的名称、开关、冻结、锁定、颜色、线型以及当前层仍重新读取，
  不跨请求缓存集合或值，保留既有明确COM拒绝和瞬态属性读取重试。
- 快照和环境读取各输出一条`structlog`事件：`tianzheng.read.snapshot`与
  `tianzheng.read.environment`，包含`duration_ms`和`completed`。
  `completed`仅表示函数正常返回，**不表示所有可选字段存在或后置校验通过**。
  耗时包括该函数内的读取和局部等待，不包括记录自身写出、STA排队、mutex和HTTP。
  没有逐getter写日志，也没有改变响应格式。
- 快照主体经AST比较与基线一致；前后全图、未选对象、表格字段、图纸身份、
  revision、代际、PID和新鲜context检查均未删除。没有增加并行COM、跨请求缓存、
  类型字段过滤、makepy生成或任何自定义对象工厂。

### 相同独立图纸上的新旧交错结果

正式顺序为`A2 → B2 → B3 → A3`，每块15个热态`inspect`，每版共30个样本。
这是**四个大块的ABBA**，不是原建议的15个单请求ABBA块；时间漂移和块内相关性
仍是限制。每块前仅重启MCP服务并核验部署hash，不重启CAD；预热、部署、落盘和
请求间等待不计入热请求墙钟。每块还有2个单墙测量对照，因此其每版仅4个样本。
每个inspect之前重读context，每块末次measure之后再做完整inspect和context检查。

| 操作 | 每版样本 | 旧版中位数 | 新版中位数 | 旧版p95 | 新版p95 |
|---|---:|---:|---:|---:|---:|
| 全图inspect | 30 | 6.066s | 5.746s | 8.829s | 6.269s |
| catalogue，limit=1 | 30 | 11.831ms | 12.541ms | 26.446ms | 22.841ms |
| transaction.context | 30 | 12.246ms | 11.522ms | 19.859ms | 16.354ms |
| 单墙TGetExtend | 4 | 9.471s | 9.481s | 不报告 | 不报告 |

inspect中位耗时减少约**0.321s / 5.3%**，是包含新增日志开销的本次净观察值，
不是所有命令的加速承诺。单墙测量没有显示提速；它不读取图层环境，仍保留两次
全图快照。p95用nearest-rank计算，保留了旧版最长10.630s的样本；没有CPU遥测，
不能把尾延迟差异都归因于代码，也不宣称统计显著性。没有独立测出日志本身的开销。

新版正式30个inspect的服务端读回分段中位数：全图快照**4.686s**、图层环境
**1.028s**。两段各自中位数不能相加当作HTTP中位数；它们也不是COM RPC耗时。
主成本仍在对象快照，按类读取计划与串行批量读取仍需单独验证，不在本次实现中。
guard/STA队列、mutex、pipe、journal分段和局部重试计数也仍待补齐。
